WHY ITEMS 2 AND 4 ARE THE POINT
  A sanitizer that reports nothing looks identical whether the subject is clean or
  the instrumentation never reached it. That is not hypothetical: the fuzzing this
  replaces spent its first run watching none of md4c, because `-Zsanitizer=address`
  went through RUSTFLAGS while the C was compiled beside it — coverage 1023 -> 2487
  when CFLAGS was added (measured 2026-08-17, recorded in CLAUDE.md). Lake compiles
  this same C into the executable today, so the premise is live.

  So each file gets a defect injected into a copy of itself and each injected defect
  is run twice, the second time with **that one file** built without
  `-fsanitize=address` and everything else unchanged. Items 1 and 3 firing while 2
  and 4 stay silent is the evidence that the instrumentation is attributed to the
  file named and not to the harness or the runtime around it. Item 6 is the actual
  question; items 1-5 are what make its silence mean something.

  Item 1's injection is a `volatile` load and not a longer input. A longer input does
  make md4c read past the end, but md4c hands those bytes to the text callback and
  `md_events.c` copies them out with `memcpy` — and ASan intercepts `memcpy` in every
  translation unit including uninstrumented ones, so item 2 would have been red with
  nothing wrong and item 1 would have proved nothing about md4c.c.

FOUND WHILE BUILDING IT — bash 3.2 turns a `set -u` abort into exit 0
  With `set -euo pipefail` and **any** EXIT trap — `trap "true" EXIT` is enough — a
  script that dies on an unbound variable exits 0; without the trap the same script
  exits 1 (measured 2026-09-02, GNU bash 3.2.57 on macOS). The trap sees `$?` already
  0, so `tools/lib/common.sh`'s `on_exit`, which captures the status and returns it,
  cannot recover it either. A plain `set -e` command failure is not affected, and
  bash 5 is not affected, so CI never shows it.

  13 scripts under `tools/` combine `set -u` with an EXIT trap. Five are `ci` rows
  and are covered by CI's bash; `base-ir-gate.sh` and `deps-docs-gate.sh` are
  `manual`, which is where the hole is open. The new gate defends itself with a flag
  set on every path that is a real answer, and a cleanup that refuses a 0 no path
  claimed. The other twelve were not changed.

WHAT THIS DOES NOT ANSWER
  - It is not the product build. Lake compiles this C with elan's clang against
    `csrc/libc`'s shim headers and no `-O` flag; the gate uses the machine's `cc`
    against real headers at `-O1`. The compiler half is already a compared quantity
    (`LITEDOC4_SYSTEM_CC=1`, `tools/libc-shim-gate.sh`); the `-O` half is not, so a
    defect that appears only at the product's optimisation level would not show here.
  - The corpus is twelve committed files, not an exploration. New entries came from
    libFuzzer runs that no longer exist in HEAD.
  - Nothing here asserts the event stream is *right*. That is
    `test/Litedoc4Test/MdParse.lean`'s subject, and the rendered HTML is
    `test/Litedoc4Test/MdOracle.lean`'s.
