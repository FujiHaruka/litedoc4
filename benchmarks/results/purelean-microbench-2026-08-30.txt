pure-Lean replacement study — the floor Lean pays, against the Rust renderer
============================================================================
2026-08-30

WHAT THIS MEASURES
  Whether replacing the Rust half of litedoc4 with Lean is affordable. This
  file is step one and answers only the narrow question: how long does Lean
  take to do the *unavoidable* parts of `litedoc4 render` — read the IR, parse
  it, parse the link index, look names up in it, build the page strings and
  write them — with **none of the rendering logic in it**. A renderer written
  in Lean cannot beat these numbers; it can only be slower.

  The Rust side of the comparison is the real `litedoc4 render`, logic and all.

CONDITIONS
  hardware      Apple M1, 8 cores, 16 GiB, macOS 26.6.1
  page cache    warm (wall clock == user+sys on every run; run 1 discarded)
  target        /Users/haruka/dev/lean-projects (InformationTheory + Mathlib)
                422 modules, 4,584 declarations
  IR            schema 5, 15,233,730 B across 422 files, generated 2026-08-30
  link index    10,448,225 B, 261,672 entries, format #lidx2
  HTML output   24,546,157 B across 422 pages (Rust); the Lean floor builds
                24,551,960 B of the same shape
  Lean          leanprover/lean4:v4.31.0, `lake build` (-O3), no Mathlib

THE COMPARISON, PHASE BY PHASE
  link index (read+parse)   Rust ~0.09 s   Lean 0.263 s    2.9x
  everything else           Rust ~0.26 s   Lean 0.404 s    1.6x  (Lean has NO
                                                                  logic in it)
  whole command             Rust  0.40 s   Lean 0.667 s+   1.7x and rising

READ THIS AS
  **Not** "Lean is 1.7x slower than Rust". The Lean side is a floor with the
  renderer removed and the Rust side is the finished renderer, so the honest
  statement is: **a pure-Lean renderer starts 0.27 s behind before it renders
  anything**, and whatever the rendering logic costs is added on top.

  The Lean floor is not yet Lean's best. `lidx.parse` is 35% of it and is
  written the obvious way — `String.splitOn "\n"` over 10.4 MB, which allocates
  261,672 strings before a single one is used. A ByteArray scan should move it.
  Whether it moves it enough is the next measurement, and until it is taken the
  2.9x on the link index is a fact about *this* implementation, not about Lean.

WHERE THIS SITS IN THE WHOLE BUILD
  A full build of this target is extraction 14.08 s (1 thread) / 6.50 s
  (--jobs 4) plus rendering (measured, docs/approach-performance.md 6.1). At
  0.40 s the Rust renderer is 6% of the 1-thread build. Tripling it costs the
  full build ~6%, which is not the reason to keep or drop Rust. The incremental
  build is where the Rust half is 73% of the work (6.5), and that is measured
  separately.

OPEN
  - math: this target has none, so nothing here says what `math-core` costs to
    replace. A Mathlib-shaped target has 2,123 math spans (measured
    2026-08-22, mathml-2026-08-22.txt).
  - the incremental path (IR full reads, ledger, impact) is not in this file.
  - the CI axis (a cargo build or a release download, against a `lake build` of
    a Lean renderer) is not in this file.

NOTE ON THE FIRST VERSION OF THIS BENCHMARK
  It reported `lidx.parse 0.000001` and `html.build` at half the real cost.
  Lean is lazy: `timeIt (pure (parseLidx text))` times the allocation of a
  thunk. Every phase here returns a `Nat` computed inside `IO` and printed, so
  the work happens inside the timer. A phase whose number looks impossibly good
  is the first thing to distrust.
