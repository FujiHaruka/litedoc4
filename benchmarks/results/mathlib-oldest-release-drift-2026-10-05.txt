Mathlib's oldest release in the window printed by the newest Lean + Mathlib: v4.29.0 -> v4.34.1, plain and through the reader
===========================================================================================================================
Date: 2026-10-05. Context: docs/multiversion/plan.md D10 (an old version is printed by the newest Lean + Mathlib, an
accepted approximation). The two earlier points were measured 3 minor releases apart (v4.31.0 -> v4.34.1):
benchmarks/results/mathlib-printer-drift-2026-10-04.txt (plain drift) and
benchmarks/results/olean-reader-prototype-2026-10-04.txt (own .olean reader + hybrid environment). This run takes the
widest distance in the current set, 5 minor releases apart, with the same two methods.

QUESTIONS
---------
(A) Plain drift: the old version's declaration type (the Expr obtained by Lean v4.29.0 itself and transported through
    the drift log's JSON serialization) printed by Lean v4.34.1 + Mathlib v4.34.1 against v4.29.0's own print.

    byte-identically to v4.29.0's own serialization (the gate), and how does the hybrid (newest import, v4.29.0
    constants and data-extension entries in place) print the same 5,000?

The reader at v4.29.0 (B): it survives. Oracle 5000 of 5000 identical, 0 not found, 0 different, before any hybrid
run (the gate). Every Name hash (11,093,084), Level data word (266,212) and Expr data word (125,014,912) decoded over
the closure equals the one v4.29.0 stored. What v4.29.0 needed, one record per writer selected by version string AND
githash (the layout log's differences, each handled explicitly):
  - header / compactor / ModuleData / Import / kernel objects (Name, Level, Expr, ConstantInfo, every *Val):
    unchanged (layout log: 0 changes in the window); the same decoders run. Header verified on the files: magic
    "olean", version byte 2, flags 1, "4.29.0", githash 98dc76e3c0a9b856c9b98726b713fb04fab16740 (= `lean --version`
    of <toolchain v4.29.0> and the layout log's tag SHA), base address at offset 80.
  - namespacesExt (v4.29.1 -> v4.30.0, #12840): v4.29.0 registers it as `Lean.namespacesExt` (public), v4.34.1 as
    `_private.Lean.Namespace.0.Lean.namespacesExt`. The reader decodes v4.29.0's entries under the v4.29.0 name and
    emits them under v4.34.1's (31,296 entries), and refuses data that carries the private name. Same entry type
    (Name) on both sides (read from both toolchains' source). v4.29.0 did not export them sorted (3,000 modules'
    entries out of Name.quickLt order); the reader sorts them, as v4.34.1's writer does. v4.34.1's importer folds them
    into a HashMap, so the order is a convention here, not a correctness requirement.
  - exportedAxiomsExt (new in v4.30.0) and eqnOptionsExt (new in v4.31.0): absent in v4.29.0. They are 2 of 76
    extensions that v4.34.1 + Mathlib v4.34.1 register and v4.29.0 + Mathlib v4.29.0 do not (registered-name diff,
    measured, list below). The v4.29.0 record names all 76; an entry under any of them stops the read (made to fail
    once, HOW IT WAS RUN). None of the 76 is among the 11 decoded extensions; in the hybrid they keep the newest
    entries like every non-decoded extension, in the old environment alone they are empty.

    private declarations' entries from .olean/.olean.server; .olean.private holds everything in both versions. The
    reader takes ModuleData from the last part (.olean.private), so nothing changes. Mathlib v4.29.0 is 3-part like
    v4.31.0: of the 10,448 .olean files on the search path, 10,438 have .olean.server + .olean.private.
  - ReducibilityStatus: v4.29.0 has the 4-constructor enum with 3 = "unfolded at .instances or above" (added in

  per release; v4.30.0 (4 apart) and v4.32.x / v4.33.x are unmeasured. The causes are individual renames, removals
  and new notations; they accumulate per release and are not linear.
