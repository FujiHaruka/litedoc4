Mathlib itself as the documented package — one `litedoc4 build`, end to end
============================================================================
2026-10-03

What this answers
-----------------
Can HEAD litedoc4 produce a complete site for the `Mathlib` library, meaning one page
per module, reconciled by name against the module list? The last attempt (prototype
era, 2026-08-11 → mathlib-scale-summary.txt §4) stopped at 767 / 8,169 pages on
`declNameToLink: no defining module for Setoid.iseqv`. Render at Mathlib scale had
never run in the pure-Lean tree.

Answer: yes. The run exits 0 with 8,170 of 8,170 module pages, and every one is
matched by name. The whole run took 4,995.7 s (83 min). 4,551.1 s of that (91%) is one
quadratic sort in the global step. A one-line patch, run separately and labelled
below, brings the global step to 38.2 s and writes byte-identical output.

3. What the 4,551 s are: one O(m²) sort
---------------------------------------
Two stack samples, at about +23 min and +54 min into the global step, both show the
same frames:
  fullGeneration → buildGlobal → derive (+3420) → Array.qsort.sort (sortUtf16) →
  qpartition loop → cmpUtf16.
derive+3420 is the return address of the `bl sortUtf16` at 0x100099ee4, and the next
call is dedupSorted. That makes it src/Litedoc4/Global/Artifacts.lean:197:

  let kinds := dedupSorted (sortUtf16 kindList)

kindList holds one cssKind string per declaration: 311,415 entries but only 8
distinct values (theorem 230,936, def 42,375, instance 29,409, ctor 4,519, class
1,958 (class 1,952 plus class_inductive 6), structure 1,586, inductive 317, opaque
315). Lean core's Array.qsort (v4.31.0, Init/Data/Array/QSort/Basic.lean) uses a
Lomuto partition. Elements equal to the pivot never go left, so a run of m equal keys
costs m²/2 comparisons and peels one element per partition (the samples show one
`sort` frame and no recursion depth, which fits). Σ m²/2 over the kinds ≈ 2.80e10
comparisons, dominated by theorem's 2.67e10.
A standalone copy of cmpUtf16 + sortUtf16 (leanc -O3, same machine) sorting n
copies of "theorem":
  n =  5,000    2.79 s   223 ns/comparison
  n = 10,000   10.82 s   216 ns/comparison
  n = 20,000   44.66 s   223 ns/comparison
  n = 40,000  182.05 s   227 ns/comparison      (×2 n → ×4 time)
This ran concurrently with the build, on a different core. These rates are an upper
bound, not the run's rate: 2.80e10 × ~220 ns ≈ 6,200 s, which is more than the whole
4,551 s global step. If the comparison count is right, the real run averaged no more
than ~160 ns per comparison (inferred, not measured). The standalone copy is not the
product binary, which Lake compiles.

At InformationTheory's scale this sort is too small to notice. At Mathlib's it is
91% of the run.

PATCHED (a scratch copy of 54d2d52, not src/; one line changed):

  let kinds := sortUtf16 (kindList.foldl (fun acc k => acc.insert k)
                 (Std.HashSet.emptyWithCapacity 16 : Std.HashSet String)).toArray

`litedoc4 global --ir <the run's IR> --out … --state … --root <clone>`, once:
  38.18 s real, 35.91 user, 0.53 sys, maximum RSS 639,827,968 B
  all 9 files it writes (404/foundational_types/index/search.html, instances.json,
  modules.json, search-index.bin, declarations/name-map.json,
  declarations/used-by.json) and global-state.json byte-identical (cmp) to the
  unpatched build's
With the patch, an unchanged build would take ≈ 4,995.7 − 4,551.1 + 38.2 ≈ 483 s
(extrapolated: the global figure comes from a separate `global` process, not a
patched `build`).

The patch fixes one call site. The general form is that sortUtf16 (and the
`keys.qsort byteLt` in Global/State.lean) is quadratic in the length of any run of
equal keys. Every `dedupSorted (sortUtf16 …)` site is therefore exposed in
proportion to its duplication. The other one in derive (instances per class, line 74)
is small here.
