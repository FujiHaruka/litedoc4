テストの穴を埋めた回 — カバレッジの前後と、数え方そのものの訂正【実測 2026-08-24】
================================================================

計画は `docs/plans/test-coverage.md`。**カバレッジの数値を目標にせず**、「検査するものが
1 つも存在しない利用者経路」を選んで潰した回。**出た製品の欠陥は 1 件**で、それは
カバレッジの低い場所からではなく、**14 サブコマンドを横断して同じ問いを投げた形**から出た。

機材と条件
----------
  Apple M1 / macOS 26.0 / Rust 1.97.1 (8bab26f4f) / cargo-llvm-cov 0.9.0。
  llvm-tools-preview は 2026-08-24 に入れた (それまで無かった)。

  母数は **`cargo test --workspace` が走らせるものだけ**。
  **ゲート (`tools/*.sh`)・e2e・`#[ignore]` の 22 本は 1 つも入っていない。**

  **llvm-cov 下と素の `cargo test` で母数が違う**:

      素の cargo test   46 バイナリ / 564 passed / 0 failed / 22 ignored
      llvm-cov 下       39 バイナリ / 553 passed / 0 failed / 21 ignored

  差は **doctest** — `cargo llvm-cov` は既定で回さない。
  **どちらの数字を引用しているかを書かないと、後から突き合わせられない。**

  page cache も暖機も無関係 (カバレッジは決定的な整数)。壁時計は記録しない。

数え方 — ここを間違えた
-----------------------
  **本体だけの行カバレッジは `--lcov` から数える。**

      mise exec -- cargo llvm-cov --workspace --no-fail-fast --lcov --output-path cov.lcov
      # 各 src ファイルの最初の `#[cfg(test)]` より手前の `DA:<行>,<count>` を数える

  lcov は 1 行につき 1 つの count しか出さないので、行の数え方に判断が要らない。

  **最初は `--json` の segments から数えて 81.6% と書いた。これは誤りだった。**
  1 行に複数のリージョンが乗る (`?` のエラー経路が同じ行の別リージョンになる) ため、
  行ごとにどう畳むかで答えが動く:

      リージョンの最小を取る    81.6%   ← 最初に書いた値。過小
      リージョンの最大を取る    87.3%   ← 過大
      llvm-cov 自身の per-file  その間  ← ファイルごとに違う畳み方
      --lcov                    86.9%   ← 採用

  症状は具体的だった: `litedoc4-md/src/parse.rs` を 71% と報告したが、llvm-cov 自身は
  87.7% と言う。**16 ポイントの食い違いが、そのファイルを「穴」に見せていた。**

  **同じ理由で、生の per-file 値もそのままでは読めない** — `#[cfg(test)]` 内のコードが
  分母に入るので、`#[ignore]` テストを多く抱えるファイルが不当に低く出る。
  `litedoc4/src/packages.rs` は生で 53%、本体だけなら 85%。**未カバーの 8 割が
  ignored テスト自身のコードだった。** 補正しないまま直しに行けば空振りする。

watch.rs の 71 行は「未検査」ではない — 測定の側が嘘をつく
----------------------------------------------------------
  **`run_loop` の中で実際に走っていて、`crates/litedoc4/tests/watch.rs` が
  その log を assert している。** カバレッジに出ないのは、`watch` を終わらせる手段が
  signal しかなく、テストが `Child::kill()` (SIGKILL) を使うので
  **子プロセスの profraw が flush されないから**。

  同じ lcov で `litedoc4/src/main.rs` が 39/39、`queries.rs` が 333/335 なのは、
  **そちらの子が正常終了するから**。同じ「実バイナリを起動するテスト」でも、
  子の終わり方でカバレッジの見え方が変わる。

  一般形: **カバレッジが 0 と言う行は、「走っていない」か「走ったが記録されなかった」の
  どちらか。** 長命プロセスを signal で止めるテストは後者を作る。

何が出たか
----------
  **製品の欠陥 1 件**:

    `litedoc4 ledger --help` だけが使い方を出さず、exit 2 で
    `unknown ledger subcommand ` + '`--help`' と拒否していた。14 サブコマンド中これ 1 つ。
    `ledger` はフラグのループの前にサブコマンドを取る唯一のコマンドで、`--help` は
    ループの中でしか見られていなかった (`ledger check --help` は動く)。

    **見つけ方がカバレッジではない。** 残り 743 行を「エラー伝播 (`?` / `map_err` /
    `panic!`)」とそれ以外に機械的に分類したら、上位 12 ファイルの「それ以外」の先頭に
    `"--help" | "-h" =>` が並んだ。**14 コマンドを横断して 1 本で問う形にして初めて、
    1 つだけ違うものが浮いた。** ファイルを 1 つずつ読んでいたら出ていない。

    **見逃されていた理由が `crates/litedoc4/src/cli.rs` の docstring にあった** —
    「14 のうち 11 がこう答える。**他の 3 つは違い、どちらの差も意図的である**」と書いて、
    **2 つしか説明していない。3 つ目は誰も決めていなかった。**
    **合わない数だけが唯一の兆候だった。**

  **記述の誤り 2 件** (どちらも「要る/走らない」と書いてあることを、走らせずに信じていた):

    - `tools/watch-gate.sh` のヘッダ「計測対象・そのtoolchain・171 MB の Mathlib extractor
      が要る」。**そのすべてが引数だった** (`--target` / `--lib` / `--module` /
      `EXTRACT_BIN`)。`e2e/micro` に対して 12 checks / 0 failed、4.0〜6.1 秒で走る
      (→ watch-gate-e2e-2026-08-24.txt)。`ci.yml` の `e2e-micro` ジョブに載せた。
      **反証は同じファイルの、その主張のすぐ下にあるフラグ一覧だった。**
    - 「`config-gate.sh` / `usedby-gate.sh` が CI で 1 度も走らない」。**両方走っていた** —
      `tools/e2e-micro.sh` が内部で呼んでいる。**ゲートの呼び出しは 2 段ある**ので、
      workflow の grep だけで数えると走っているものを走っていないと数える。

  **製品の欠陥はこれ 1 件だけ。** 26 通りの変異 (段 2 で 8 / 段 3 で 7 / 段 4 で 11) を
  当てて、赤くなったものは他にすべてテスト側の期待の誤りだった。

  ついでに、書いたテストが「何をしても通る」形になっていたのを 1 件捕まえた:
  `litedoc4-incr` の名前の省略 (10 個まで見せて残りを数える) に、10 個と 17 個の
  ケースだけを書いていた。**ちょうど 11 個という境界が空いていて、`>` が `>=` に
  滑る変異が逃げた。** 境界を両側から見るテストに直したら捕まるようになった。

やらないと決めたもの
--------------------
  - **`litedoc4-md/src/parse.rs` の未カバー 52 行** — 1 行ずつ読んだら **50 行が
    `Error::Malformed` 系の防御分岐**だった。`Error` の docstring 自身が
    "Every case is a bug here or a change in md4c, never bad input" と言っている。
    埋めれば 88% → 100% になるが、**増えるのは数字だけで検査は増えない。**
  - **段 6 の P2〜P5** — 残り 724 行は `?` の伝播、getter、`--serve` の常駐経路
    (機材が要る = ゲートの領分)、診断用フラグ (ゲートが既に読んでいる)。
    **壊れたときに利用者に当たると 1 行で言えるものが無い。**
  - **カバレッジのしきい値を CI のゲートにすること** — 壁時計をゲートにしないのと
    同じ理由。数値が落ちたときに「何が壊れたか」を 1 行で言えず、`#[ignore]` の増減でも動く。
