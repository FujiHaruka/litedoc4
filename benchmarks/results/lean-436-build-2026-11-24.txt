Does litedoc4 build on Lean v4.36.0, and does the .olean reader run on it?
=========================================================================

Working tree on 67df801 (main) plus the v4.36.0 changes, uncommitted at the time.
Apple M1 Pro, 32 GB, macOS 26.7.1. Run 2026-11-24.
leanprover/lean4:v4.36.0, leanGithash 611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9 (`lean --githash`).

(0) What v4.36.0 changes (measured)
  Docstrings. The text Lean stores for a doc comment no longer ends with the spaces and newlines
  before its `-/`. In v4.36.0's Lean/Parser/Term.lean, `commentBodyFn` ends the text atom before
  the trailing run of ' ' and '\n' and makes that run the atom's trailing whitespace, and
  `getDocStringText` returns the atom. Probe files elaborated on v4.35.0 and on v4.36.0, each
  docstring read back with `findDocString?` / `getMainModuleDoc` (11 declaration docstrings, a
  tactic's `syntax` docstring, a module docstring, 6 indentation shapes of the closing line, 2
  carriage returns before `-/`; the first file again with CRLF line endings): in every case
  v4.36.0's string is v4.35.0's with the trailing run of ' ' and '\n' removed. A tab, a carriage
  return and U+00A0 end the run and stay in both. The CRLF copy gives the same strings as the LF
  one on both versions, so a CR before `-/` from a CRLF file is not observable.

  On e2e/micro the two versions' IR differs in 103 docstrings (92 declaration and field `doc`, 11
  module `text`): 103 of 103 end in ' ' or '\n' on v4.35.0, 0 of 103 on v4.36.0. Besides those,
  only leanVersion, extractorIdentity, contentHash and bytes differ. Of the rendered sites, the
  data blobs the 17 HTML pages name (data-data, data-page, data-used-by) differ in the Lean
  version, Init's source root and 32 integers in the page blobs' name tables; HAdd.hAdd
  (1481 -> 1489) and Iff (183 -> 181) among them were checked against the two Leans' sources as
  declaration lines. No other file of the sites was compared.
  Recorded as column 3 of tools/lean-toolchains.txt (`kept` for v4.31.0 .. v4.35.0, `dropped` for
  v4.36.0). The extractor writes what Lean returns, as before.

  The .olean layout. Lean.Elab.PartialFixpoint.EqnInfo has a ninth field, `fixEq? : Option Name`.
  The reader built on v4.36.0 failed with "Entries.lean:251:9: error: Fields missing: `fixEq?`".
  Now each writer record states the layout (8 fields for 4.29.0 .. 4.35.0, 9 for 4.36.0), the
  decoder takes it from the record, and the oracle prints it as a `layout` line next to the one
  Lean's own `getCtorLayout` gives. In v4.36.0's Init, Std and Lean, one module carries entries
  under that extension (Std.Data.Iterators.Lemmas.Equivalence.Basic, one entry,
  Std.BundledIterM.Equiv, fixEq? none), so a `some` in the ninth field is decoded by nothing here.
  The same module carries one on 4.29.0, 4.31.0, 4.33.1 and 4.35.0 (`dump carriers`), so a record
  with the wrong layout is refused by the decoder before the oracle writes its `layout` line: that
  line has passed 13 times and has not yet failed on its own.

  Registered extensions: v4.36.0 registers the same 197 as v4.35.0. For each of the 13 writer
  records, `reader --absent-extensions` equals the set difference of v4.36.0's registered
  extensions against that Lean's (4.29.0 and 4.29.1 56, 4.30.0 43, 4.31.0 23, 4.32.x 15, 4.33.x 6,
  4.34.x 2, 4.35.0 0), so no older record changed. ImportState, ImportedModule and CompactedRegion,
  which the reader mirrors, are unchanged.
