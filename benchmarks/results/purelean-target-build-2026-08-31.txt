Reproducibility
---------------
A second Lean run into a fresh `--out`, same session, same inputs: identical to
the first Lean run in every file **including `litedoc4-build.json`**, except the
same three extractor-written timing files. Re-compared against the Rust run it
reproduces the result above exactly. So the agreement is a property of the two
implementations, not of one lucky pair of runs.

What this found
---------------
1. **`work/ledger-timings.json` is written by the Rust `build` and not by the
   Lean one.** `crates/litedoc4/src/build.rs` hands `build_ledger` a `timings`
   path unconditionally in `full_generation`; `src/Litedoc4/Build.lean`'s
   `fullGeneration` discards the `BuildPhases` the same call returns.

   It was **not** fixed here, and the reason is not effort. The file's four
   values are all durations, so writing it could never make the tree identical —
   it would only move this line from "missing" to "differs". Its fifth field is
   `concurrency`, which Rust fills from `hash_concurrency()` (8 here) and Lean
   would have to fill with 1, because the Lean ledger hashes one module at a
   time (`sequentialNote`, decided at M4 → `purelean-sha256-2026-08-31.txt`).
   Writing 8 from the Lean half would be recording a parallelism that did not
   happen. So the choice is between "absent" and "present and different", and
   nothing in this repository promises the file: it is a diagnostic in `work/`,
   it is on no gate's list, and `tools/public-surface.txt` does not name it. It
   is recorded here so that M9 decides it rather than discovers it.

2. **The `external note:` on a missing `lake-manifest.json` is one line in Rust
   and two in Lean, with the path repeated.** Both halves build it from the same
   template (`{path}: {e}. Without it no dependency's revision is known …`); the
   difference is entirely inside Lean's rendering of `IO.Error`, which is
   multi-line. That is the **second** consequence of a divergence M7 already
   decided (Rust `No such file or directory (os error 2)` against Lean
   `no such file or directory (error code: 4294967294)`); M7 recorded the wording
   and not the shape. Writing a one-line renderer for `IO.Error` is the same
   thing M7 refused — transcribing another runtime's error table.
   Measured on a `--root` that is not a Lake package: both halves exit 3, and
   **stderr is byte-identical**; only this one stdout line differs.

3. **`tools/site-compare.sh` carried the doc-gen4-era artefact list** — the same
   six names `tools/site-artefacts.txt`'s header records `clone-gate.sh` having
   carried, five of which litedoc4 deliberately does not write. On two identical
   litedoc4 sites it printed

       artifacts : -4/6 of the whole-package six identical

   a negative count nobody could attribute. The fix that had already been made
   in `clone-gate.sh` on 2026-08-29 had not been raised to its general form: the
   judgement lived in a third place. It now reads `tools/site-artefacts.txt` and
   counts absent apart from differing (a reference from another generator has
   none of these, which is not the same answer as having them and disagreeing).
   Made to fail twice before being believed: renaming `search-index.bin` in the
   inventory printed `11/12 … 1 absent`, and hiding the inventory exits 2.

   The line does not decide the verdict, and did not before: what fails a
   comparison is the whole-tree missing / extra / differing count.

4. **`tools/build-gate.sh` hardcoded `RUST_BIN=$REPO/target/release/litedoc4`** —
   the same defect the four `*-reference.sh` had at M5. It now reads `LITEDOC4`,
   the spelling `tools/*-reference.sh` and `tools/watch-gate.sh` use, and
   `conditions()` records the binary that produced the numbers
   (`litedoc4  <path> (<--version>)`) beside `rustc`. Nothing else in the gate
   assumed the Rust half: the stdout lines `counts()` greps and the
   `plan    incremental` / `0 to re-extract` strings gates 2 and 3 look for are
   written by both halves from the same spellings, and `--full`, `--lib`,
   `--jobs`, `--link-index`, `--extractor-bin` and `--timings` are all
   implemented on the Lean side since M7.

Why build-gate has no verdict here (measured)
---------------------------------------------
The gate needs an APFS clone of the target whose **own oleans were rebuilt at the
clone's path** (`tools/rebuild-own.sh`), and this machine could not afford it
today. The clone itself is free — `cp -Rc` of the 12 GB tree took 35.9 s and cost
about 0.1 GiB — but the rebuild is a from-scratch `lake build` of 422
Mathlib-dependent modules on 16 GB of RAM, and:

    free on /            5.8 GiB after the clone
    free on /            3.8 GiB ~90 s into the rebuild, 57 of 422 oleans done
    /System/Volumes/VM  28 GiB -> 30 GiB over the same interval

The 2 GiB that left the disk went into swapfiles, not into build products, and
macOS did not give it back when the build was killed (free returned to 3.8 GiB
after the clone was deleted; the VM volume stayed at 30 GiB). Extrapolating the
same rate over the remaining 365 modules puts the run past the free space, and
the failure mode when this disk fills is the one already recorded for
2026-08-17: the target repository's own state breaks and the means of recovery
goes with it. The run was stopped and the clone removed; the target was verified
untouched (705 oleans, one untracked path, the same as before).

So `build-gate.sh` was exercised as far as it can be without a clone:

  * `LITEDOC4=/nope/litedoc4` → `missing: /nope/litedoc4 — run: cargo build
    --release -p litedoc4, or set LITEDOC4`, exit 1 (the break-once).
  * `gate4` with `LITEDOC4` pointing at a stub that prints its argv and exits 7 →
    the gate reported `litedoc4 build FAILED (exit 7)` and the log held the stub's
    own name and the full argument list, so the call site drives whatever
    `LITEDOC4` names.
  * `gate4` driven by each real half over a fake `--root`: both exited 3, the
    gate reported both identically, and their stderr was byte-identical (this is
    where finding 2 came from).
  * `gate4` completed end to end against a stub that writes the shape the gate
    counts, so `conditions()` really printed
    `litedoc4  <path> (litedoc4 0.0.0-stub)`.

What is still not measured
--------------------------
**The Lean half is built on one toolchain only.** `tools/lean-toolchains.txt`
promises four rows (v4.31.0 / v4.32.2 / v4.33.0 / v4.33.1); `ci-lake.yml` runs
the `purelean-*` gates at whatever `e2e/consumer/lean-toolchain` pins, which is
v4.31.0, and `ci-lean-versions.yml`'s matrix — one job per row of that file —
drives `tools/e2e-micro.sh` with `cargo build --bin litedoc4`, i.e. the **Rust**
half.
So no workflow has ever compiled `src/Litedoc4/` against v4.32.2 or v4.33.0.
Everything above is v4.31.0 / macOS arm64. Do not read it as "probably fine" —
that is the shape the extractor's v4.33.0 build failure had (2026-08-18) and the
shape `ci-lean-versions.yml` exists to stop.
