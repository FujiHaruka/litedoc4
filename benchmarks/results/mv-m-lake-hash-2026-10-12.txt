M, one version natively: the build's ledger reads Lake's <file>.hash instead of hashing olean bytes
===================================================================================================

Conditions: Apple M1, 16 GB, macOS 26.6.2; Lean v4.33.1, Mathlib v4.33.1 (0df444a360); the M slice
(438 modules, 1,314 olean files, 330,315,448 B). Same checkout as
mv-m-parallel-hash-2026-10-11.txt and mv-m-stream-ir-2026-10-11.txt. litedoc4 at 085ee58 (before)
and 085ee58 + `build` taking the `lake` algorithm (after); extractor from 085ee58 in both arms.
Warm (a cold first run, 22.03 s, discarded). One run per arm (the user's rule for levers).

command  litedoc4 build --root <checkout> --lib Mathlib --out <empty> --extractor-bin <x> --jobs N
         --timings <file>, under /usr/bin/time -l

Hash files present (measured): 1,314 of 1,314 olean / olean.server / olean.private files in the
slice have a <file>.hash beside them. Mathlib's cache (Cache/IO.lean, mkBuildPaths) packs
olean.hash as required and olean.server.hash / olean.private.hash alongside their oleans.

Exactness (measured): ir/, site/, store/, link-index.lidx(.key) equal by diff -r between the j4
arms. ledger.json differs in exactly `algorithm` (sha256 -> lake), 1,314 file hashes, 1,314
`bytes` (-> -1) and 438 module hashes. render-ledger.json differs only in `renderer` (the
executable's digest); litedoc4-build.json only in the store path.

Change detection under the lake ledger (measured, on the j4 after-output):
  second build, nothing touched          incremental, extract 0, 1.64 s
  one module's olean.hash overwritten    incremental, extract 1 (that module), 4.40 s
  (the file restored and compared byte for byte afterwards)
  ledger check with one olean.hash removed: refuses naming the missing file, exit 1.

What the ledger now trusts: the 64-bit content hash Lake wrote when it built or unpacked the
olean. An olean rewritten without its <file>.hash is not seen as changed.
