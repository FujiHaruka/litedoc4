THE MECHANISM
-------------
`reader extract --write-reuse-keys` writes, beside the IR, `<--ir-dir>.reuse-keys`: a header with
the printing identity (the extractor identity line with the running Lean's version and githash
in place of the version read's: source digest, output flags, reader digest, readerLean,
readerLeanGithash) and one line per candidate of the target modules, `<name>\t<key>`. The key:
kind, level parameter names, Lean's structural Expr.hash of the type, the type's top-level binder
names and binder infos, the value's Expr.hash for a definition or opaque (0 for every other kind;
a theorem's proof is never read), and for an inductive each constructor (name, type hash, its
top-level binder names and infos) plus, for a structure, its parents (structure, projection) and
flattened field names. It is written outside the IR directory (`store put` reads every file
under it) and does not change the IR or the link index (gate below).
`reader extract --reuse-from <dir>` (implies --write-reuse-keys) reads <dir>/index.json, every
module file it lists and <dir>.reuse-keys. When the printing identity differs nothing is reused.
Otherwise a declaration whose own key equals its key there is handed to the extractor's existing
reuse hook (the one `reader session` uses) with its printed parts read back from that IR:
binders, implicits, type, binderCode, typeCode, equations, equationCode, members (field docs then
recomputed) and the names in refs. Everything else is computed as without the flag: positions,
index, docstrings, attributes, kind and instance status, modifiers, sorry, generated origin, the
module half of refs (resolved by writeIRTree in this version's environment), the dependency maps
and the link index. A name in the IR that does not read back to the same string is not offered
(0 such names on M). `reader session` refuses both flags: exit 2 at start-up, `err` per request.
