=== 1  THE HOLE, AND HOW WIDE IT IS

A script that dies on an unbound variable is asked what it answers. The only
variable is the `set` line and whether an EXIT trap is installed.

  #!/bin/bash
  set <LINE>
  <trap 'true' EXIT, or nothing>
  echo "value: $NOPE"
  echo "should not reach"

  set line             trap         bash 3.2   bash 5.3.9
  set -euo pipefail    yes          exit 0     exit 1
  set -euo pipefail    no           exit 1     exit 1
  set -uo pipefail     yes          exit 1     exit 1
  set -uo pipefail     no           exit 1     exit 1

  `set -e` is what makes it a hole. Under `set -uo pipefail` the abort is
  reported as 1 whether or not a trap is installed; under `set -euo pipefail`
  with a trap, bash 3.2 answers 0 for a script that died. bash 5 never does.

  Nothing inside the trap can tell that apart from a clean fall-off:

  -- died on an unbound variable
  /var/folders/n2/1dbjyx3s0y7g8yk_v3stw9bw0000gp/T/tmp.PhmxvLOy7p/c.sh: line 4: NOPE: unbound variable
    trap sees rc=0 BASH_COMMAND=[echo "value: $NOPE"]
  -- fell off the end
    falls off the end
    trap sees rc=0 BASH_COMMAND=[echo "  falls off the end"]

=== 2  THE GUARD

`answer_required` up front, `answer <status>` on every path that exits 0, and
an EXIT trap that turns a 0 no path claimed into 70. `exit 70` and not
`return 70`: under `set -uo pipefail` a trap's return value is discarded.

  set line             path                 bash 3.2   bash 5.3.9
  set -euo pipefail    set -u abort         exit 70    exit 1
  set -uo pipefail     set -u abort         exit 1     exit 1
  set -euo pipefail    answer 0             exit 0     exit 0
  set -uo pipefail     answer 0             exit 0     exit 0
  set -euo pipefail    answer 1             exit 1     exit 1
  set -euo pipefail    unclaimed fall-off   exit 70    exit 70
  set -uo pipefail     unclaimed fall-off   exit 70    exit 70
  set -euo pipefail    set -e abort         exit 1     exit 1
