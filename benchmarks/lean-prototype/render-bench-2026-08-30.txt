pure-Lean replacement study — what the rendering logic costs on top of the floor
================================================================================
2026-08-30. Reads after `purelean-microbench-2026-08-30.txt` and
`purelean-microbench-optimised-2026-08-30.txt`, which measured the floor with no
rendering logic in it. This one measures a Lean renderer that does the job.

WHAT WAS MEASURED
  `benchmarks/lean-prototype/Render.lean` — 1,612 lines (1,298 non-comment,
  of which 316 are the JSON/`.lidx`/byte/escape infrastructure copied from
  `Main.lean`) — against `litedoc4 render` on the same IR, the same `.lidx` and
  the same output directory shape.

  It renders: the document frame (head, theme boot, topbar, sidebar shell,
  module head with its `source` link), the import list with a relative link for
  every own-package import, and every declaration in page order — anchor id,
  kind, modifiers, binders, type, attributes, structure fields, equations, the
  `source` link with its `#L<a>-L<b>` range, the docstring — plus **autolinking**:
  the span-tree walk over every printed code fragment resolving each constant
  through the declaration's own `refs`, then the IR's map, then the `.lidx`, and
  `autoLinkInline` over every word of every docstring code span.

  LEFT OUT: **Markdown and math.** A docstring goes in escaped, with its
  backtick-delimited code spans found by a byte scan rather than by a parser.
  See "WHAT IS MISSING" for the size of that.

CONDITIONS
  Identical to the two earlier files: Apple M1, 8 cores (4 P + 4 E), 16 GiB,
  macOS 26.6.1, Lean v4.31.0 `lake build` (-O3), no Mathlib, warm page cache.
  IR 422 modules / 15,233,730 B / 4,584 declarations; `.lidx` 10,448,225 B /
  255,809 declaration entries + 6,011 `@` module entries.
  Rust: rustc 1.97.1 --release, `target/release/litedoc4` built 2026-08-29 13:02
  — the same binary that wrote `pages/` and that the 0.40 s comes from. It
  predates the `sorry` / `@[ext]` pill commit (25af76d), so its output has 0
  `data-flag` elements, and the Lean side matches the binary, not HEAD.
  n=6, run 1 discarded, medians of 5.

WHERE `page.render` GOES — ablations, each removing one part and nothing else
  (n=3, one back-to-back set; control 0.6415 in that set)
  what                                            cost     share
  frame, module head, imports, decl heads, toc,
    section markup, HTML escaping, string build   0.2993    47%
  code-fragment walk (span tree, UTF-16 offsets,
    whitespace rewrite, escaping)                 0.1357    21%
  const-link resolution (refs -> known -> .lidx)  0.0754    12%
  docstrings (backtick scan + autoLinkInline)     0.1311    20%
  ----------------------------------------------------------
  page.render                                     0.6415

  The link resolution — the phase this study expected to dominate — is 12% of
  the rendering and 7.7% of the whole command. `lidx.lookup` looked like the
  largest single phase in the floor because the floor probed all 261,672 keys
  **four times**, 1,046,688 probes. A renderer does not: it probes once per
  const span that resolves to a module, and this target's rendered fragments
  hold **127,047 const spans of which 127,041 resolve** (measured over the IR),
  plus one probe per docstring code-span word that resolves. The floor's
  `lidx.lookup 0.1442` is therefore about 8x the traffic a renderer generates,
  and the floor is not a lower bound on that one phase.

WHAT IS MISSING, WITH A SIZE
  **Markdown.** 4,885 docstrings, 1,625,158 B. Of those bytes, 455,212 (28.0%)
  are inside the 25,139 backtick code spans this renderer does scan and
  autolink; the remaining 1,169,946 B (72.0%) go in escaped where Rust runs md4c
  over them and emits paragraphs, headings with ids and hover anchors, lists,
  tables and links. That is the 355,103-byte and 2,168-anchor shortfall.
  **Nobody has measured what md4c costs on this input**, so the honest reading
  is that the Lean numbers here are a floor for a renderer that also does
  Markdown, not an estimate of one.
  **Math.** 2 of 422 pages carry MathML on this target and `math spans kept as
  LaTeX 0`, so it is invisible in these numbers — but not on a Mathlib-shaped
  target (2,123 spans, `mathml-2026-08-22.txt`).
  **`sorry` / `@[ext]` pills.** 2 declarations carry a `generated` key. The Rust
  binary that produced the comparison output predates the feature and emits 0
  pills, so the Lean side emits none either.
  **The unescaped-module-spelling map** (`module_for_unescaped`): no module of
  this target has a quoted component, so the map is empty and the branch is not
  implemented.
  **Everything outside a module page**: `index.html`, `search.html`, the assets,
  the search index, `modules.json`, the incremental ledger.

READ THIS AS
  A pure-Lean renderer that does the same autolinking as the Rust one, on this
  target, costs **0.98 s sequential and 0.51 s on 4 threads**, against the Rust
  renderer's **0.40 s single-threaded**. So: **2.6x sequentially, 1.3x with four
  threads against a Rust binary that has not been threaded at all** — and 2.7x
  the CPU sequentially, 3.3x threaded.

  The gap is not concentrated where this study kept looking. The link index is
  0.13 s of it and the const-link resolution 0.08 s; the other 0.77 s is spread
  evenly over *touching bytes* — parsing 15.2 MB, escaping and assembling 24 MB,
  walking 385,880 spans through a UTF-16 offset map. That is the same 10-cycles-
  per-byte the optimised floor file identified, and no restructuring moves it.

  What is not measured here is Markdown, which is 72% of the docstring bytes and
  a C library on the Rust side, and the incremental path, where the Rust half is
  73% of the work.
