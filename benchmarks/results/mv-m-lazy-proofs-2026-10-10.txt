THE RULE
--------
Decided per theorem, before its ConstantInfo is built, from its own module's exportedAxiomsExt
entries (decoded first, names only): the proof is decoded iff the module stores no axiom list for
the theorem, or the list holds sorryAx. Every other theorem gets the reader's omitted proof (a
constant no environment defines). Readers of theorem values in a read-alone run:
- Lean's collectAxioms (the sorry tag asks it for every analysed declaration): an imported name
  with a stored list is answered from the list and its body is never walked; only a name without
  one is walked, and the rule decodes exactly those. The hybrid places the old entries by key in
  the module the environment gives each name (finalizeHybrid refuses an index mismatch), sorted
  by Name.quickLt, so Lean's lookup finds the same list the rule read.
- the extractor's mentionsSorryAx: asked only when collectAxioms answered sorryAx, so the theorem
  either had sorryAx in its list or no list: decoded either way.
- mechanism 3's closure check: it checks the names the decoder saw. With the flag it checks types,
  definition bodies, entries and the proofs the run decodes; names that occur only inside an
  omitted proof are not checked (references 862,629 -> 716,629 on v4.33.x, 853,381 -> 708,779 on
  v4.32.2; 0 dangling in both arms).
- the kernel during addDecl of realized lemmas: the extractor runs with debug.skipKernelTC true,
  so nothing is type-checked and the kernel never unfolds a proof.
- the equation generator's TransparencyMode.all sites (WF/Fix.lean, WF/Unfold.lean,
  DefEqAttrib, the delaborator's whnf of function types): in Lean v4.34.1 Meta's whnf never
  unfolds a theorem at any transparency. getUnfoldableConst? and getUnfoldableConstNoEx?
  (Meta/GetUnfoldableConst.lean) both answer none for a theorem, and Meta.getTheoremInfo has no
  caller, so no Meta path reads a proof body through unfolding. Had one unfolded it, the omitted
  proof's name would throw "unknown constant" on the first path and stay a stuck term, silently,
  on the NoEx one. The IR oracle below is what answers for both, and it answered equal on every
  file.
- Mathlib's eqns attribute and the equation lemmas getEqnsFor? returns: names, printed through
  inferType (types only). The autoParam sameValue comparison reads value? of tactic definitions,
  never of theorems. PrintKey and the patch read values only in `reader session`, which refuses
  --lazy-proofs (a carried constant could have been decoded under an axiom list since changed).

**Verdict: exact, and lower in memory in every process; faster at --jobs 1 by the plan's rule,
not separated at --jobs 4 on this run.** By the plan's three criteria E2 wins at one job and fails
the time criterion at four, where the product runs. The time it removes is in the decode phase,
which does not depend on --jobs (2.7-2.9 s at one job, 1.3-3.1 s at four).

  Against the prediction (decode 12-14 -> 6-7 s, peak -0.5 to -0.8 GiB; extrapolated):
