pure-Lean replacement study — the incremental path (impact / ownership / merge)
==============================================================================
2026-08-30. The fifth measurement. The first four are the floor
(`purelean-microbench-2026-08-30.txt`), the floor written properly
(`purelean-microbench-optimised-2026-08-30.txt`), the renderer
(`purelean-renderer-2026-08-30.txt`) and the renderer with Markdown
(`purelean-markdown-2026-08-30.txt`). This one is the *other* half of the Rust
tree: the three commands that carry the IR full reads
(`docs/approach-pillars.md` §5.6 names the full read as the rate limiter).

WHAT WAS BUILT
  `benchmarks/lean-prototype/Incr.lean`, 1,079 lines of Lean, no dependencies
  outside Lean core (not even MD4Lean). The JSON scanner, the typed IR and the
  byte helpers are copied from `Render.lean`, for the reason its own header
  gives. It does what `litedoc4 impact`, `litedoc4 ownership` and
  `litedoc4 merge` do:

    impact     both closures — IMPORTERS (reverse transitive import closure cut
               to the package's own modules) and REFERRERS (direct and
               transitive over the `refs` edges) — the census columns, the
               `--print-set` in UTF-16 order and the summary JSON.
    ownership  the re-extracted-vs-base name diff, and the base-side sweep for
               `(defining module, name)` pairs that no longer hold, with both
               rules (`lostOwner` / `movedElsewhere`) and the witnesses.
    merge      module-file carry, `contentHash` comparison, the dependency slice
               recomputed from the merged module files, stale `deps/*.json`
               removal, and the merged `index.json` with the base file's key
               order and the weakest `schemaVersion`.

CONDITIONS
  Apple M1, 8 cores (4P+4E), 16 GiB, macOS 26.6.1, Lean v4.31.0 `lake build`,
  rustc 1.97.1 --release (binary built 2026-08-29 13:02), warm, n=6, run 1
  discarded, medians of 5, **all rows interleaved in one loop** so no two come
  from different cache states. Wall from `time.monotonic`, CPU and RSS from
  `wait4`'s rusage — the same fields `/usr/bin/time -l` reads, at finer
  resolution; a separate `/usr/bin/time -l` pass agrees to its 0.01 s grid.
  Target: the same 422-module / 15,233,730 B IR as the four earlier files.

THE INPUT, AND WHY IT IS NOT THE ONE ON DISK
  `ownership` and `merge` need a partial ("inc") tree. The one the reference
  incremental run left behind
  (`purelean/incr.work/self-one/work/inc-ir-1`) is a **`ledger touch`**: the
  olean is untouched, so **not one name moves**, `watching` is false, and
  ownership never reads the base at all. That is exactly the simulation §5.6
  says gives 3.00 full reads and is wrong.
  So a second inc tree was built (`purelean-incr/inc`): the base's
  `InformationTheory.Shannon.ChannelCoding.Basic` with its most-referenced
  declaration renamed (`…ChannelCoding.jointSequence` ->
  `…jointSequenceRenamed`, 34 modules name it). 1 name lost, 1 gained, so the
  base-side sweep runs. **Both implementations were given the same tree.**
  Both trees are measured below.

ABLATION — is the gap the typed conversion or the scan?
  `impact` needs only `module`, `imports`, each declaration's `name` and its
  `refs`. Rust has no choice: `serde` deserialises the whole `ModuleFile`,
  spans, members, equations and all. `--slim` gives the Lean side the same
  licence a real implementation would take.

    Lean, full `toModule` (like for like)   0.1907 s   2.60x
    Lean, `--slim`                          0.1726 s   2.35x
    difference                              0.0181 s   9.5% of the command

  **The typed conversion is not where the gap lives.** Dropping every field the
  stage does not read buys 9.5%, and the remaining 2.35x is the JSON scan over
  15.2 MB — the same ~10 cycles per byte the optimised floor file identified and
  the renderer file confirmed. `--slim`'s output is identical to Rust's.

WHY `merge` IS THE CHEAP ONE (1.34x, against 2.6-2.8x for the other two)
  `merge` is not one read: it is one read plus 422 module-file copies and 4
  files written. Rust's wall (0.1828) is well above its CPU (0.1289) — 0.054 s
  of it is I/O the CPU is not doing — and that part costs the same in either
  language. Its own instrumentation splits it
  `modules 0.050 s / deps+index 0.129 s`; the Lean split is
  `modules.copy 0.055 s / deps.scan 0.182 s` with the ~0.006 s of `deps` and
  `index.json` writing outside both phases. So the copy half is **1.10x** and
  the full-read half **1.41-1.45x** — and the copy half is Lean's worst case for
  the comparison, because `fs::copy` on macOS is a kernel-side copy while this
  prototype does `readBinFile` + `writeBinFile` through user space, and it still
  loses only 10%.
  **The more a stage does that is not parsing, the smaller the Lean penalty.**

MEMORY — the one place Lean wins outright
  `impact` Rust 56.2 MB, Lean 10.4 MB. Rust's `impact` materialises every
  `ModuleFile` into a `Vec` and holds them all; Lean's reference counting frees
  each module the instant its four fields have been extracted. This is
  retention, **not** work — the Lean side parses exactly the same 422 files —
  and Rust could do the same by extracting as it goes.

`lake build incr` — the number the CI axis needs
  4.23 s real / 4.33 user from clean (Incr only; the package's other targets and
  MD4Lean untouched), 1,079 lines, no dependencies. Compare the renderer's
  4.52 s for 1,612 lines. Nothing new is downloaded: `Incr.lean` imports only
  `Std.Data.HashMap` / `Std.Data.HashSet`, so unlike the renderer it adds **no**
  git dependency and none of the +6.1 s the MD4Lean checkout costs.

WHAT IS NOT IN THIS
  - `--census`, `--changed-file`, `--exclude`, `--removed`, `--remove`,
    `--modules`, `--timings`, `merge --verify` and the `Unrecognised` mode:
    parsed by the Rust CLI, not implemented here. `impact`'s census *columns*
    are computed (the closures are), the TSV is not written.
  - The refusals. Rust refuses an unknown mode, a changed module that is not in
    the package, a module list that does not describe the tree, a schema too
    old, and an `--out` that resolves to `--base` via `..`. This prototype
    refuses only the second. **A stage's error paths are most of its 365 / 330 /
    773 lines**, and they are not in the 1,079.
  - `detect`, `ledger` and `prune`, the other three stages of the incremental
    path. They read `index.json` and the ledger, not the module files, so they
    carry no full pass — which is why they are outside the question this file
    was measuring.

READ THIS AS
  **2.60x / 2.82x / 1.34x sequentially, for output that is identical — a 422-line
  set, a 34-line set and a 426-file IR tree, compared with `diff` and `diff -r`.**
  The incremental path is **not** worse for Lean than the renderer was: it is the
  same 2.6-2.8x wherever it is parsing and better wherever it is not, and at four
  workers all three land at or under Rust's single-threaded wall clock. The
  reason the ratio never moves is the reason the renderer file gave: the cost is
  bytes touched, not the kind of work done on them.
