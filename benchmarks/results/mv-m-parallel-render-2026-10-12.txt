M, one version natively: the render's per-module and per-file stages on --jobs workers
===================================================================================

Conditions: Apple M1, 16 GB, macOS 26.6.2; Lean v4.33.1, Mathlib v4.33.1 (0df444a360); the M slice
(438 modules). Same checkout as mv-m-lake-hash-2026-10-12.txt. litedoc4 at 3a7c648 (before) and
3a7c648 + the parallel render (after), both built with Lean v4.31.0; extractor from 085ee58 in
every arm. Warm (a discarded warm-up per binary). One run per arm (the user's rule for levers).

Profile of the render before (measured, one thread, `store render` on the M store entry, ms)
  store read (unpack)            220   sequential
  parse 438 module IRs           705   per module
  facts                           84   per module
  derive                         326   whole version
  name index                      10   whole version
  pages                          924   per module
  Used by + lists                 98   whole version
  render (data and shells)       180   whole version (not parallelised)
  gzip + write data files        700   per file
  -> ~2.4 s of ~3.3 s is per-item work.

  build j4 before  13.40 s   33.39 s    3.251 s         13.301 s       222.8 MiB

  How the extra memory grows with the worker count was not measured (only 1 and 4).
