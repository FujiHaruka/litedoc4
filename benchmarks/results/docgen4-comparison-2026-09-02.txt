WHY ONCE AND NOT AS A GATE
  doc-gen4 is not in the target's manifest (10 packages under .lake/packages, none of them
  doc-gen4), so `lake update` there or a `.lake` wipe destroys this oracle for good and
  nothing in this repository can re-mint it. A standing comparator over a dying oracle would
  have to grow an exception list. These three questions were `#[ignore]`d Rust tests until
  `crates/` left HEAD on 2026-09-02; they are the five that step E of M10 recorded as having
  no surviving home, minus the two whose expectations are committed.

  What they are for: `tools/public-surface.txt` promises that page paths and declaration
  anchors keep doc-gen4's shape. Today that promise is held only by `e2e/micro-expected`,
  49 files minted from litedoc4's own output, which cannot say whose shape it was to begin
  with. This answers that at 422 modules of Mathlib-depending Lean.

FALSIFICATION — a gate does not check itself
--------------------------------------------------------------------------------
Each arm was made to fail once before its green was allowed to mean anything
(benchmarks/tools/docgen4-compare-falsify.py). Baseline green; every perturbation red:

  RED  Q1 anchor: one declaration id changed
       → litedoc4 rendered ['…modelCode_x'], which doc-gen4 has no anchor for
       → doc-gen4 has an anchor for …modelCode, which is in today's IR for this module
  RED  Q1 order: two declarations swapped
       → the page order differs somewhere other than a tie
  RED  Q1 docstring: a word invented
  RED  Q1 docstring: the long words dropped
       → a module docstring differs and neither the tree's age nor MathML explains it
  RED  Q1 source links: one file path changed
       → the source links name different files
  RED  Q2 roots: Mathlib deep module pointed elsewhere
  RED  Q2 roots: Init pinned to another revision
       → want …/blob/68218e…/src/Init.lean
  RED  Q3 declaration URLs: 40 line ranges shifted
       → 25 of 251,225 resolvable .lidx entries disagree with doc-gen4

Two things the falsification itself turned up, and both are the reason it was run:

  1. The first attempt was GREEN on a changed anchor id. The perturbation had not landed —
     the page it was applied to had almost no declarations, so the replace matched nothing.
     The script now refuses to run a case whose perturbation did not change the input.
  2. The first Q2 perturbation was GREEN. It moved Mathlib's root-module URL, and the tree
     has no page for the Mathlib root module, so that field is never compared. Perturbing the
     field that is compared turns it red.

  Of the 40 shifted .lidx ranges, 25 were detected: the other 15 are names the oracle does
  not carry (fields and constructors), which is the same 16,040-entry bucket Q3 reports.

WHAT THIS RUN DOES NOT SAY
  - It is not a byte-reproduction result. doc-gen4 compatibility ended at M8 and is not
    redefined; what is compared is anchor identity and order, module docstring text, source
    link file paths, and source URLs.
  - The `#L…-L…` half of every source link is not compared on the page arm. The tree is
    older than the sources.
  - 81 of the target's 422 modules have no page in the tree and are not compared at all.
  - The oracle cannot be re-asked once the target's .lake is wiped or updated.
