Print reuse starting from the native extraction of the newest version: why it was refused, and the fix
=====================================================================================================

An inspection run, not a gate (2026-10-10). E6's chain (docs/multiversion/implementation.md, "Levers
plan", item 5) builds versions newest first, each older one reusing prints from the one just built.
The newest is extracted natively, and `reader extract --reuse-from` refused the native IR, so the
runner measurement read v4.34.1 a second time through the reader to get keys: 361.25 s and 457.85 s
on the runner (measured -> mv-l-reuse-2026-10-10.txt, "head (crutch) wall").

WHY IT WAS REFUSED (read off the code and the keys headers)
-------------------------------------------------------------
1. The native extractor wrote no keys file: the key, the candidate list and the keys writer lived in
   the reader only.
2. The keys header carries a printing identity, and the reader's was its IR identity: source digest,
   Lean, output settings, plus reader=, readerLean=, readerLeanGithash=, which a native run never has.
3. Found while fixing 2: the source digests differ too. The reader compiles Extract.lean with `main`
   cut off, so its source= digest (7bb4d9f8122fd2b8 before this change) was not the native binary's
   (f0c4... before; the whole file).
The output settings (equations, refs, tagged code, no-equations-under) already matched: both paths
take their flags from one function in litedoc4.

THE FIX
-------
- The cheap key (ownKey, the member names it hashes, shownHash, the candidate list) and the keys file
  writer move into Extract.lean, so both binaries compute the same key from the same code, and the key
  code is under the source digest. Key values unchanged (below).
- The printing identity is the identity line over Extract.lean with `main` cut, the printing Lean and
  the output settings, without the reader fields. The IR's own identity (index.json) is unchanged.
- The native extractor takes `--write-reuse-keys` (needs --write-ir), writing the same file the reader
  writes. Not yet passed by `build --versions`.
- Two #guards, each made to fail once on a scratch copy: the printing identity ignores the reader
  fields and moves with everything else; the cut matches the reader's and cutting twice changes
  nothing. Extract.lean compiles on v4.31.0, v4.32.2, v4.33.0, v4.33.1, v4.34.1.

In `build --versions` the reader's new roots are the newest version's own module list, the one its
native extraction imports, so the two import sets are equal there by construction; this 14-module
run is the case where they are not. Nothing checks it: the printing identity does not name the
import set.
Saved per full build (theoretical, unverified on the runner): the crutch's 361-458 s, less the native
build's own key writing (keys took 18.1 s on one thread on the runner before keys went parallel).
