Unicode table regenerators: what can still be re-asked, and what cannot
=======================================================================

Subject         the enumerated Unicode tables shipped in src/, and whether a
                live oracle still exists for each after M10 deletes crates/

Five tables in three files, not the three a previous note recorded
------------------------------------------------------------------

  src/Litedoc4/Md/Gc.lean         pzcTable, zcTable     UnicodeBasic
  src/Litedoc4/Global/V8Gc.lean   v8ZcTable             V8
  src/Litedoc4/Lower.lean         lowerTable,           Rust's str::to_lowercase
                                  sigmaTable

The generators live in tools/oracle/ and write **Rust**, into paths M10
deletes:

  gen-gc-table.ts     -> crates/litedoc4-md/src/gc.rs
  gen-v8-gc-table.ts  -> crates/litedoc4-global/src/v8_gc.rs

lowerTable / sigmaTable have **no generator anywhere in the tree** (searched
tools/ and benchmarks/tools/). Their oracle is the Rust standard library,
which leaves the tree entirely at M10 — a strictly worse position than "the
generator writes Rust".


1. V8's Z | C re-derives identically today (measured)
------------------------------------------------------

Regenerating the set from this deno's own /[\p{Z}\p{C}]/u and comparing
against the string committed in src/Litedoc4/Global/V8Gc.lean:

    produced ranges  737
    produced chars   7817
    committed chars  7817
    result           IDENTICAL

So the Lean table is re-askable with deno alone — no target, no Mathlib, no
Rust. A CI gate over this one is viable and would be green today.


2. gen-v8-gc-table.ts --check is red, and no gate runs it (measured)
---------------------------------------------------------------------

    deno run --allow-read --allow-write tools/oracle/gen-v8-gc-table.ts --check
    exit 1
    "crates/litedoc4-global/src/v8_gc.rs is not what this script produces"

The whole difference is **prose in doc comments** — 30 diff lines, every one
of them rewording a `//!` or `///` block (a "Not the renderer's table" heading
added, two sentences reordered, one spot-check comment expanded). **No range
moved and the pinned-runtime line did not move**, which is what item 1
independently confirms.

The file's own header says `Generated by tools/oracle/gen-v8-gc-table.ts; do
not edit.` It was edited by hand anyway, and `--check` — the one thing that
would have said so — is run by **no gate**: tools/gates.txt has no row that
re-derives any of these tables.

This is the "a check nobody runs" shape from CLAUDE.md, in its quietest form:
the edits improved the prose, nothing broke, and the file has simply been out
of agreement with its generator ever since. Whoever repoints the generator at
Lean must carry the improved wording **into the generator**, not re-emit the
older prose over the top of it.


3. UnicodeBasic cannot be asked at all right now (measured)
--------------------------------------------------------------

gen-gc-table.ts shells out to `lake env lean --load-dynlib=<UnicodeBasic>` in
the target. Neither the library nor the package is there:

    .lake/packages/UnicodeBasic                 absent
    lake-manifest.json packages                 mathlib, plausible,
                                                LeanSearchClient, importGraph,
                                                proofwidgets, aesop, Qq,
                                                batteries, Cli,
                                                InformationTheory

**doc-gen4 is not in the manifest either**, and doc-gen4 is what brings
UnicodeBasic. So pzcTable / zcTable have no runnable oracle on this machine
today, and restoring one is a `lake update`-scale operation on a Mathlib
project. Disk at the time of measurement: 2.4 GiB free of 228 GiB (99% used),
which is not room for it.

Consequence for the repoint: the **emitter** half of gen-gc-table.ts can be
changed and verified (feed it the ranges the committed table already encodes
and require it to reproduce that table byte for byte). The **acquisition**
half — dump-gc.lean through `lake env` — is unchanged by such a repoint and
stays as untested here as it already was. Do not describe a repointed
gen-gc-table.ts as verified end to end; it would not be.


What this means for the three cases
-------------------------------------

  v8ZcTable            live oracle, deno only. Re-derives identically today.
                       Can carry a CI gate.
  pzcTable, zcTable    oracle exists in principle (UnicodeBasic, as doc-gen4
                       links it) but is not installed. Manual at best.
  lowerTable,          no generator, and the oracle is the Rust standard
  sigmaTable           library, which M10 removes. V8 does **not** stand in
                       for it — 28 code points disagree (section 4). No live
                       oracle survives M10 for these two.


4. V8 cannot stand in for Rust's str::to_lowercase (measured)
---------------------------------------------------------------

The open question at the end of section 3, settled the same day and in the
same session, on the same deno as section 1.

Method: decode lowerTable's 185 runs, evaluate lowerOf(cp) for every code
point 0..0x10FFFF (surrogates skipped), and compare against
String.prototype.toLowerCase() of that one code point. Only the 1,112,063
code points where V8 answers with a single code point are compared; the one
multi-code-point answer is U+0130, which src/Litedoc4/Lower.lean already
special-cases outside the table (as it does U+03A3).

    runs decoded      185
    code points       1112064 (surrogates skipped)
    v8 single-cp      1112063
    v8 multi-cp       1
    DISAGREEMENTS     28

All 28 go the same way — **our table lowercases the code point and V8 leaves
it unchanged**:

    U+A7CE  -> U+A7CF     v8: unchanged
    U+A7D2  -> U+A7D3     v8: unchanged
    U+A7D4  -> U+A7D5     v8: unchanged
    U+16EA0 -> U+16EBB    v8: unchanged   (and U+16EA1..U+16EB9 alike, +0x1B)

That is a UCD version gap, not a semantic disagreement: Rust's character data
has assignments this deno's V8 does not. **So V8 is not a drop-in oracle for
lowerTable**, and the answer would silently change with the deno version if it
were used as one.

Consequence: lowerTable and sigmaTable have **no live oracle inside this tree
once crates/ is gone**. Re-deriving them needs either a Rust toolchain (the
thing M10 removes) or the UCD files themselves (UnicodeData.txt,
SpecialCasing.txt, DerivedCoreProperties.txt), which are not vendored here.
Freezing them is defensible; freezing them *without saying so at the
definition* is not, because the file currently reads as though a regenerator
exists.

Note the direction of this result: it refuses the cheap answer. Had the two
agreed, the conclusion "V8 is the replacement oracle" would have been the
convenient one and would have needed more doubt than this one does.
